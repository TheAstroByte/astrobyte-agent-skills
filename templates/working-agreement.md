# Operator working agreement

## Work context

Describe the operator's roles, strong areas, learning areas, common project types, and the amount of explanation that helps.

## Scope and autonomy

Record the selected autonomy preset. State what the agent can change without another question and what always requires approval. Translate the operator's definition of good code into concrete review and verification rules.

## Delivery modes

Define explore, prototype, durable, and production expectations. Record the personal default and the conditions that require a project-specific choice.

## Code and dependencies

Record maintainability rules, stack preferences, dependency policy, prohibited tools, and the treatment of coherent existing projects.

## Verification

State the proof expected for behavior, APIs, user interfaces, data work, and model quality. Keep code correctness separate from empirical quality.

## External actions and unattended work

Record approval, cost, time, data-transfer, and stop boundaries. Configuration can narrow authority but cannot grant permissions that the active agent does not have.

## Review

Record the reviewer model. Name the newest model in the chosen family, and state that its reasoning level follows the harness default. Record when a second reviewer is required. When the agreement names no reviewer, setup asks once and offers to record the answer here.

## Git and communication

Record isolation, issue, review, update, explanation, and challenge preferences. State whether agent-created commits use dual attribution, agent-only attribution, human attribution with an agent trailer, or disabled attribution. Keep ordinary human Git identity unchanged.
